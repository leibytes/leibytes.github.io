# 商圈积分交易通知\+会员与微信/支付宝ID的绑定方案

**适用场景：**租户自收银、资金不进商场、租户贴原生静态收款码、商场侧只通过商圈交易通知发放积分；**当前只有微信小程序，没有支付宝小程序**。

**核心结论：**微信支付 openid 在微信小程序内通过商圈积分插件完成事前绑定；支付宝 buyer\_id 受生态隔离限制，无法在微信小程序内获取，需要在支付宝 App 内打开 H5 网页完成授权绑定；两套绑定共用一张 `member_pay_account_bind` 表，CRM 会员以手机号为唯一主键。

# 一、方案总体约束与边界

## 1\.1 业务背景

- 商场入驻微信商圈、支付宝商圈，获取商圈 ID 与门店档案。

- 租户使用自己的微信商户号、支付宝 PID 收款，资金直入租户账户，商场不碰资金、不做二清。

- 商场只接收商圈推送的交易通知，按规则向顾客发放积分。

- 租户收银侧不改码、不改收银系统，使用原生静态收款码。

## 1\.2 关键认知（必须先对齐）

1. **商圈回调报文本身不包含商场会员号、手机号、CRM ID**，只包含支付侧交易信息与付款人平台唯一标识（微信 openid / 支付宝 buyer\_id）。

2. **会员识别逻辑完全在商场积分中台**，通过"支付唯一标识 ↔ CRM 会员"的绑定关系表做二次映射。

3. **绑定关系不是商圈自动给的**，必须由顾客主动授权、商场系统主动获取支付标识后入库建立。

4. **杜绝冒领**：不开放"手动输入交易单号认领订单"入口，绑定动作必须在付款账号本人的微信/支付宝环境内完成，并做付款账号身份强校验。

## 1\.3 生态隔离硬限制

|能力|微信生态（微信小程序内）|支付宝生态|
|---|---|---|
|获取微信支付 openid|✅ 支持，通过微信商圈"会员快速积分"官方插件授权回调获得|❌ 不支持，无法跨生态调用微信接口|
|获取支付宝 buyer\_id（2088 开头）|❌ 不支持，微信小程序内无法拉起支付宝 OAuth，也拿不到支付宝用户标识|✅ 支持，需要支付宝小程序或支付宝网页应用（H5 OAuth）|
|顾客可用载体|微信小程序（已具备）|支付宝 App 内 H5 网页（需新建支付宝开放平台网页应用）|

# 三、微信支付 openid 绑定流程

该链路在**已有的微信小程序内**完成，是主推的无感积分方案。

## 3\.1 前置准备

- 商场已入驻微信商圈，创建商圈 ID 与门店档案。

- 微信小程序引入官方"商圈会员快速积分"插件。

- 配置插件授权回调地址（商场中台 HTTPS 接口）。

## 3\.2 绑定步骤

1. 顾客在微信小程序内通过手机号验证码登录 CRM，拿到 `crm_member_id`。

2. 进入"商圈积分"页面，加载商圈积分插件，顾客主动授权商圈积分服务。

3. 微信服务器回调商场中台配置的授权通知地址，推送**商圈支付域 openid**（与后续商圈交易通知报文里的 openid 同源）。

4. 中台校验唯一约束：该 openid 是否已绑定其他会员；若已绑定则拒绝并提示。

5. 写入绑定表：`crm_member_id + pay_channel=1 + pay_account_id=支付 openid`。

**最高频坑点：openid 三者隔离**

小程序 `wx.login` 拿到的 openid、公众号 openid、商圈支付域 openid 是三套独立体系，**不能混用**。绑定表只能存商圈插件回调推送的"支付域 openid"，否则商圈交易通知过来一定匹配不到会员。

# 四、支付宝 buyer\_id 绑定方案（重点：仅微信小程序）

## 4\.1 为什么不能在微信小程序里做

- 微信小程序环境与支付宝生态完全隔离，无法拉起支付宝 OAuth 授权。

- 没有正规接口可以在微信小程序内获取支付宝 buyer\_id。

- 如果做"输入框让用户手动填 2088 开头 buyer\_id"，会带来冒领、刷单风险，**明确禁止**。

## 4\.2 推荐方案：支付宝网页应用（H5 OAuth）

在支付宝开放平台注册一个**网页应用（不是小程序）**，申请 `auth_base` 静默授权权限，备案域名，配置 OAuth 回调地址。开发成本远低于支付宝小程序，是当前场景下的最优解。

### 绑定完整链路

1. 前置：支付宝开放平台创建网页应用，申请用户信息授权（user\_id）权限，配置业务域名与授权回调地址。

2. 触达入口：顾客在租户门店用支付宝付款后，**支付宝商圈推送服务通知到顾客的支付宝消息列表**，通知里的跳转链接指向商场的 H5 绑定页。

3. 顾客在**支付宝 App 内**点开这条通知，H5 页面通过支付宝 OAuth 静默授权拿到 `auth_code`。

4. 商场后端用 `auth_code` 换取 access\_token，进而拿到 `buyer_id`（2088 开头）。

5. H5 页面引导顾客用手机号验证码登录 CRM（与微信小程序是同一套会员池，手机号即会员唯一键）。

6. **防冒领强校验（核心）：**比对当前 OAuth 拿到的 buyer\_id 与商圈服务通知里记录的付款 buyer\_id 是否一致；不一致直接拦截，提示"非本笔订单付款账号，无法绑定"。

7. 唯一性判断：该 buyer\_id 是否已绑定其他会员；未绑定则写入同一张绑定表：`crm_member_id + pay_channel=2 + pay_account_id=buyer_id`。

8. 绑定成功后，后续该支付宝账号在任何租户门店消费，支付宝商圈回调推送 buyer\_id，中台查表匹配会员，自动发放积分。

**防冒领原理：**绑定入口只出现在付款人自己支付宝收到的服务通知里；H5 页面强校验"当前 OAuth 账号 == 流水里的付款账号"。即使顾客把链接转发给别人，别人用自己的支付宝打开，buyer\_id 对不上，直接拦截。

## 4\.3 会员池打通

- CRM 会员主表以**手机号为唯一主键**，不要以微信小程序 openid 作为会员主键。

- 微信小程序登录（手机号验证码）与支付宝 H5 登录（手机号验证码）识别为同一会员。

- 同一个会员可以在绑定表里有多条记录：一条微信 openid、一条支付宝 buyer\_id，甚至多个微信账号。

## 4\.4 备选兜底（不推荐）

如果连支付宝网页应用都暂时不想申请，只能走人工兜底：顾客联系商场客服，提供支付宝订单截图 \+ 手机号，运营后台人工核验流水后在管理后台录入 buyer\_id 绑定。缺点是人工成本高、客诉多，不适合量大的商场。

# 五、绑定表设计

微信与支付宝共用同一张绑定表，通过 `pay_channel` 字段区分渠道。

```sql
CREATE TABLE `member_pay_account_bind` (
  `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '自增主键',
  `crm_member_id` BIGINT UNSIGNED NOT NULL COMMENT 'CRM 会员主键 ID',
  `pay_channel` TINYINT NOT NULL COMMENT '渠道 1=微信支付 2=支付宝',
  `pay_account_id` VARCHAR(128) NOT NULL COMMENT '支付唯一标识：微信=支付域openid；支付宝=buyer_id(2088开头)',
  `bind_status` TINYINT NOT NULL DEFAULT 1 COMMENT '绑定状态 1正常 2已解绑',
  `bind_source` TINYINT NOT NULL COMMENT '绑定来源：1小程序自主绑定 2运营后台录入 3活动绑定',
  `bind_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '绑定时间',
  `unbind_time` DATETIME NULL DEFAULT NULL COMMENT '解绑时间',
  `remark` VARCHAR(255) NULL DEFAULT NULL COMMENT '备注，解绑原因等',
  `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_channel_pay_account` (`pay_channel`, `pay_account_id`),
  KEY `idx_crm_member_id` (`crm_member_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='会员-支付账号绑定表';
```

## 5\.1 核心约束

|约束|说明|
|---|---|
|唯一索引 `uk_channel_pay_account`|同一个支付 ID（同一渠道）只能绑定一个 CRM 会员，防止一笔付款同时匹配到多个会员导致积分多发资损。|
|一个会员可绑多个支付账号|一个 crm\_member\_id 可以对应多行记录（微信 A、微信 B、支付宝 C），通过 `idx_crm_member_id` 索引查询。|
|软删除原则|解绑不物理删除记录，只更新 `bind_status=2` 与 `unbind_time`，保留历史链路用于对账、客诉追溯。|

## 5\.2 商圈回调匹配会员的 SQL

```sql
SELECT crm_member_id
FROM member_pay_account_bind
WHERE pay_channel = #{payChannel}
  AND pay_account_id = #{payAccountId}
  AND bind_status = 1;
```

# 六、商圈交易通知报文与会员匹配

**核心结论：**微信商圈、支付宝商圈的交易通知（回调报文）本身**不包含商场会员 ID、手机号、CRM 会员编号**，只包含支付侧交易信息 \+ 付款人平台唯一标识（微信 `openid` / 支付宝 `buyer_id`）；会员匹配是**商场积分中台做二次映射**，不是商圈直接传会员信息。

## 6\.1 报文字段速览

**微信商圈 TRANSACTION\_NOTIFY**

- `mch_id`：租户微信商户号

- `transaction_id`：微信支付单号（幂等键）

- `out_trade_no`：租户订单号

- **`openid`****：付款人支付域 openid（会员匹配核心）**

- `total_amount`：金额（分）

- `trade_state`：SUCCESS / REFUND

- `store_id`：商圈门店 ID

**支付宝商圈 alipay\.merchant\.trade**

- `pid`：租户支付宝 PID

- `trade_no`：支付宝交易号（幂等键）

- `out_trade_no`：商户订单号

- **`buyer_id`****：2088 开头买家 ID（会员匹配核心）**

- `total_amount`：金额（元）

- `trade_status`：TRADE\_SUCCESS / TRADE\_REFUND

- `store_id`：商圈门店 ID

## 6\.2 微信商圈完整报文示例（TRANSACTION\_NOTIFY）

商圈事件推送（非普通支付回调），核心字段完整示例如下：

```json
{
  "event_type": "TRANSACTION_NOTIFY",
  "mch_id": "租户微信商户号",
  "sub_mch_id": "子商户号（服务商模式才有）",
  "out_trade_no": "商户侧订单号（租户收银订单号）",
  "transaction_id": "微信支付单号【核心幂等键】",
  "openid": "付款人支付域openid【会员匹配核心标识】",
  "total_amount": 1000,
  "trade_state": "SUCCESS",
  "trade_time": "2026-10-26T12:00:00+08:00",
  "store_id": "商圈内门店ID",
  "custom_info": "商圈扩展透传字段（收银改造才有，静态码为空）",
  "refund_transaction_id": "退款单号（退款事件才有）",
  "sign_info": { "sign": "验签串" }
}
```

**匹配会员唯一标识：****`openid`****（支付域 openid）**。该 openid 与普通小程序 `wx.login` 的 openid、公众号 openid 三者互相隔离，不能混用。

## 6\.3 支付宝商圈完整报文示例（alipay\.merchant\.trade）

```json
{
  "topic": "alipay.merchant.trade",
  "pid": "租户支付宝PID",
  "store_id": "商圈门店ID",
  "out_trade_no": "商户订单号",
  "trade_no": "支付宝交易号【幂等键】",
  "buyer_id": "2088xxxxxxxxxxxx【买家buyer_id，会员匹配核心标识】",
  "total_amount": "100.00",
  "trade_status": "TRADE_SUCCESS / TRADE_REFUND",
  "gmt_payment": "2026-10-26 12:00:00",
  "passback_params": "透传参数（收银改造才有，静态码为空）",
  "extend_params": "扩展参数",
  "sign": "签名"
}
```

**匹配会员唯一标识：****`buyer_id`****（2088 开头支付宝用户唯一编号）**。buyer\_id 不是手机号，支付宝不会在报文中返回买家手机号。

**说明：**微信 `custom_info` / 支付宝 `passback_params` 只有租户收银系统主动上送才会有值；租户贴原生静态收款码时这两个字段为空。

## 6\.4 报文 → CRM 会员 完整匹配链路

以下为自收银静态码方案（主推）的完整匹配链路：

1. **接收并验签：**中台接收商圈回调，第一步验签（防止伪造请求刷积分，必做）。

2. **校验交易状态：**仅成功交易、退款事件进入业务逻辑；过滤关闭、支付失败等无效状态。

3. **幂等控制：**以平台交易单号 `transaction_id / trade_no` 作为唯一键，防止商圈重复推送回调重复发积分。

4. **提取标识：**微信取 `openid`，支付宝取 `buyer_id`。

5. **查询绑定表：**查 `member_pay_account_bind`，命中 `crm_member_id`。

6. **分支处理：**命中则调用 CRM 发放积分，并把交易单号写入积分流水做幂等；未命中则落待绑定流水、不自动发积分（兜底见 6\.5）。

7. **退款匹配：**退款事件通过原交易单号找到原积分流水，定位会员后执行积分回滚；若积分已核销，生成负积分或人工工单。

会员匹配 SQL（高频查询）：

```sql
SELECT crm_member_id
FROM member_pay_account_bind
WHERE pay_channel = #{payChannel}
  AND pay_account_id = #{payAccountId}
  AND bind_status = 1;
```

**备选链路（收银改造透传模式）：**报文 `custom_info / passback_params` 预先由租户收银塞入 `crm_member_id`，回调直接解析透传参数即可匹配会员，不再走 openid/buyer\_id 查表。局限：静态贴纸收款码不支持，租户必须改收银系统。

## 6\.5 匹配过程中的边界与异常处理

|边界 / 异常|处理方案|
|---|---|
|openid 混淆（微信最高发）|小程序/公众号/支付三种 openid 隔离；绑定表只能存商圈支付域 openid，否则商圈回调一定匹配不到会员。|
|一个支付账号只绑一个会员|唯一索引 `uk_channel_pay_account` 约束；A 微信已绑会员1，不能再绑会员2。|
|报文不带手机号|平台不返回买家手机号，禁止通过手机号反向匹配支付账号（违规）。|
|退款匹配|退款事件报文同样携带 openid/buyer\_id \+ 原交易单号，通过原单号找到积分流水定位会员扣回积分。|
|门店归属校验|报文带 store\_id，中台维护 store\_id ↔ 租户商户号映射，防止 A 店交易算到 B 店积分规则。|
|未命中会员|落待绑定流水，不自动发积分；支付宝侧由商圈服务通知引流到 H5 绑定后补发。|

# 七、注意事项与风险点

## 7\.1 最高优先级（资金与合规）

- **资金隔离红线：**本方案只做交易消息同步，商场不得截留、划转租户资金，不得修改租户结算路径，避免二清风险。

- **商户自愿授权：**租户有权拒绝加入商圈，不能强制圈店；合同需写明授权范围仅限推送交易通知用于积分。

- **幂等防重：**商圈回调会重复推送，必须以平台交易单号做唯一键，同一笔订单只发一次积分。

- **退款积分回滚：**必须订阅退款事件，退款自动扣回已发积分；积分已核销时要走负积分或人工工单。

## 7\.2 技术与稳定性

- **验签不可省略：**所有回调报文必须验签。

- **不能只依赖回调：**回调存在超时、丢消息，必须每日定时拉取平台官方流水做补偿补发。

- **商户号状态监控：**租户商户号一旦风控冻结、注销或解绑商圈，消息会断流，需要告警。

- **门店映射：**报文带 store\_id，中台维护 store\_id ↔ 租户商户号映射，避免 A 店交易算到 B 店积分规则。

## 7\.3 会员识别相关

- **禁止手动输入交易单号认领：**冒领风险高，已在本方案中明确废弃。

- **禁止手动输入 buyer\_id：**同上，所有 buyer\_id 必须来自支付宝 OAuth 授权。

- **openid 同源校验：**微信绑定表只存商圈插件推送的支付域 openid，禁止用 `wx.login` 的小程序 openid 入库。

- **手机号即会员主键：**微信小程序与支付宝 H5 共用一套 CRM，避免出现两个会员。

- **隐私合规：**绑定表只存 openid / buyer\_id，不存手机号明文；回调报文不会、也不应尝试反查买家手机号。

## 7\.4 运营与对账

- 三套账要对平：微信/支付宝商圈流水、商场积分发放记录、租户收银账单。

- 所有回调报文、验签结果、积分发放、退款回滚日志至少保存 6 个月。

- 租户退出商圈流程要提前通知运营，停止该租户积分发放。

# 八、两渠道绑定方式对比总览

|渠道|绑定入口|获取支付 ID 方式|生态限制|
|---|---|---|---|
|**微信支付**|已有的微信小程序|微信商圈"会员快速积分"插件授权回调，拿支付域 openid|无，原生支持；注意 openid 三套体系隔离|
|**支付宝**|支付宝 App 内打开 H5 网页|支付宝开放平台网页应用（H5 OAuth）静默授权，拿 buyer\_id|无法在微信小程序内完成；需新建支付宝网页应用，不能让用户手填 buyer\_id|

**一句话汇报口径：**微信支付账号直接在微信小程序接入商圈积分插件完成事前绑定；支付宝账号受生态隔离限制，无法在微信小程序内绑定，需要做一个支付宝开放平台网页应用，依托支付宝商圈的支付通知，在支付宝 App 内打开 H5 授权页面，校验付款账号身份、手机号登录同一套 CRM 后完成 buyer\_id 绑定；绑定完成后，微信、支付宝的商圈交易通知共用一张绑定表，统一匹配会员发放积分，全程不开放单号认领，规避冒领。
